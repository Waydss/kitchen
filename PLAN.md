# План реализации «Авито.Кухни»

## 1. Цели и обязательные требования

Цель — показать проектирование понятного MVP API для web-клиента и заведений. Обязательный результат: основной сервис и отдельный example restaurant service в одном репозитории, запуск через Docker Compose, PostgreSQL migrations, OpenAPI-контракт, CJM пользователя и заведения в text-based формате, C4 и схема БД, README, линтер/static analysis и тесты. Авторизация, пользовательский frontend и production-ready инфраструктура ТЗ не требуются.

## 2. Scope MVP

- Просмотр доступных заведений, карточки заведения и актуального меню.
- Создание заказа из доступных позиций только одного заведения.
- Получение заказа и истории его статусов.
- Передача заказа в example restaurant по HTTP.
- Подтверждение/отклонение заказа заведением при создании.
- Идемпотентность пользовательского запроса и внутренней передачи заказа.

## 3. Сознательно не реализуем

Нет пользовательской аутентификации, оплаты, курьеров, геопоиска, корзины на сервере, промокодов, real-time push, административного UI и сложного service discovery. Не используем Kafka, Redis, gRPC, Kubernetes и event bus: для одного заведения и MVP достаточно синхронного HTTP и PostgreSQL. Polling `GET /orders/{id}` заменяет WebSocket/SSE.

## 4. Пользовательские сценарии

Основной путь: список заведений → выбор доступного заведения → меню → локальная корзина → `POST /orders` с `Idempotency-Key` → просмотр заказа → polling статуса и истории.

Ошибки: неизвестные идентификаторы дают `404`; закрытое заведение, недоступная позиция или неверный переход — `409`; пустой заказ, разные заведения или неверное количество — `400/422`; повтор с тем же ключом возвращает прежний заказ; таймаут/некорректный ответ заведения оставляет заказ в контролируемом состоянии `restaurant_confirmation_pending` и допускает безопасный повтор доставки.

## 5. Сценарий заведения

Основной сервис отправляет заказ во внутренний `POST /api/v1/orders` example restaurant. Заведение дедуплицирует запрос по внутреннему `order_id`, сверяет внешние SKU и наличие, сохраняет свой `external_order_id`, затем синхронно подтверждает или отклоняет заказ. Kitchen сохраняет решение и только после этого отвечает клиенту. Callback для последующих переходов `preparing → ready` будет отдельным внутренним контрактом следующего этапа.

## 6. Границы ответственности

- **Avito.Кухня:** публичный каталог, снимок состава/цен заказа, конечный автомат, история, идемпотентность и единый API для web-клиента.
- **Example restaurant:** собственные SKU/остатки, решение принять заказ и статусы приготовления; это отдельный процесс и контейнер.
- **PostgreSQL:** долговременные данные, FK/UNIQUE/CHECK, атомарность и защита от дублей/гонок.
- **Web-клиент:** отображение, локальная корзина, генерация idempotency key и polling; бизнес-инварианты повторно проверяет backend.

## 7. Архитектура и компоненты

Модульный монолит на Go: `transport/http → application/service → repository → PostgreSQL`. Gin используется только в transport. Repository не знает об HTTP, service зависит от узких интерфейсов repository и restaurant client. Компоненты: `catalog`, `orders`, HTTP-клиент заведения, config, postgres pool и два `cmd` entrypoint. Интерфейсы вводятся только на внешних границах и для тестирования.

## 8. Domain model

- `Restaurant`: внутренний ID, внешний ID, название, описание, статус, URL интеграции.
- `MenuCategory`: категория конкретного заведения и порядок отображения.
- `MenuItem`: внутренний ID, внешний SKU заведения, категория, цена в копейках, доступность.
- `Order`: клиентский ID, заведение, текущий статус, итоговая цена, idempotency key, внешний ID заказа.
- `OrderItem`: ссылка на позицию плюс неизменяемые снимки названия, внешнего SKU и цены на момент заказа.
- `OrderStatusHistory`: статус, время и источник изменения.

Цена заказа рассчитывается сервером из заблокированных строк `menu_items`, а не принимается от клиента. Принадлежность позиции заведению защищается составными FK. Текущий статус хранится в `orders` для быстрых чтений, полная история — append-only в `order_status_history`.

## 9. Жизненный цикл заказа

`restaurant_confirmation_pending → confirmed → preparing → ready → delivering → delivered`.

Из `restaurant_confirmation_pending` возможен `rejected`; из `confirmed` — `cancelled` до начала приготовления. `rejected`, `cancelled`, `delivered` терминальны. Переходы валидирует service в транзакции; CHECK ограничивает множество статусов, а история добавляется атомарно с изменением текущего статуса.

## 10. База данных

Таблицы: `restaurants`, `menu_categories`, `menu_items`, `orders`, `order_items`, `order_status_history`. Все имеют UUID PK и временные метки. Основные ограничения: положительные цены/количества, уникальный внешний ID заведения, уникальный SKU внутри заведения, уникальный `(customer_id, idempotency_key)`, составные FK для связи меню с заведением. Индексы покрывают список доступных заведений, меню по заведению/категории, заказы клиента и историю по заказу. Application logic отвечает за вычисление суммы, проверку доступности и конечный автомат; БД — за ссылочную целостность, допустимые значения и атомарность.

## 11. API-first контракт

Публичное API `/api/v1`: `GET /restaurants`, `GET /restaurants/{restaurantId}`, `GET /restaurants/{restaurantId}/menu`, `POST /orders`, `GET /orders/{orderId}`. Внутренний API example restaurant документируется отдельно и недоступен с host. У ошибок единый DTO с `code`, `message`, `details`; UUID и деньги имеют строгие форматы. Health endpoints Kitchen находятся в `/health/live` и `/health/ready`.

## 12. Интеграция и обработка ошибок

HTTP-клиент имеет короткий request timeout и проверяет status/schema. `order_id` служит ключом дедупликации у ресторана. Отказ по товару становится доменным `rejected`; при сетевом сбое заказ остаётся `restaurant_confirmation_pending`, а повтор того же клиентского запроса безопасно доставляет ресторану тот же `order_id`. Это простая retry-модель без фонового worker.

## 13. Testing strategy

Unit-тесты проверяют service, HTTP-клиент, status machine и HTTP mapping. Repository integration-тесты запускаются против PostgreSQL и проверяют migrations/constraints. `make test-e2e` поднимает Compose и проходит полный пользовательский и ресторанный путь. Обязательны regression-тесты ошибок и идемпотентности.

## 14. Docker, конфигурация и observability

Multi-stage Dockerfile собирает оба бинарника. Compose запускает PostgreSQL с healthcheck, одноразовый migrator, API и example restaurant; зависимости используют health/complete conditions. Конфигурация поступает из env и валидируется при старте, секреты не коммитятся. Для MVP используются структурированные JSON-логи `slog`, request ID, status/latency и health endpoints; метрики/трейсинг оставлены на масштабирование.

## 15. Архитектурные компромиссы

Синхронный HTTP прост и нагляден, но не гарантирует автоматическую доставку после сбоя без повтора клиента; при масштабировании понадобится transactional outbox и worker. Дублирование текущего статуса и истории осознанно ускоряет чтение, согласованность обеспечивает одна транзакция. Цена хранится целым числом копеек, чтобы избежать ошибок float. Общая PostgreSQL принадлежит только основному сервису; example restaurant не читает её напрямую.

## 16. Этапы реализации

1. Каркас Go, config, HTTP server, pgxpool, Compose, Makefile и health endpoints.
2. Migrations, seed-данные и read-only каталог (`restaurants`, `menu`).
3. OpenAPI skeleton, README и первые unit/integration-тесты.
4. Создание/чтение заказа, транзакции, снимки цен и идемпотентность.
5. Синхронная отправка заказа в example restaurant и безопасный повтор по тому же `order_id`.
6. Callback последующих статусов, расширенный status machine и автоматический outbox retry.
